• 1. Today it is mixed.

  - local fs scan uses blocking threads and std::fs via Scanner / LocalFileScanner in src/
    frame/scanner_impls.rs and src/scanner.rs.
  - NFS scan uses async Tokio + nfs3_client RPCs, then bridges results into the existing local
    metadata/control-file writers in src/scanner.rs:299.
  - SMB scan is the same pattern: async SMB traversal, local sync metadata/control-file
    writing in src/scanner.rs:408.

  For backup:

  - local -> local uses the old blocking bio pipeline in src/backup/bio.rs.
  - Any path involving NFS or SMB uses aio orchestration in src/backup.rs:268 and src/backup/
    aio.rs.
  - Even in aio, only the remote copy transport is async. If the target is local, hardlink/
    delete/mtime still reuse the existing blocking local phase code via
    run_local_target_phases(...) in src/backup/aio.rs:654.

  2. Those files are direction-specific copy pipelines.

  Examples:

  - src/backup/aio/local_to_nfs.rs: local read + NFS write
  - src/backup/aio/nfs_to_local.rs: NFS read + local write
  - src/backup/aio/nfs_to_nfs.rs: NFS read + NFS write
  - same idea for SMB

  They exist because the copy phase needs to know:

  - how to read bytes
  - how to create directories
  - how to map control-file paths into source/target-relative paths
  - which post-copy phase runner to call afterward

  local -> local does not have local_to_local.rs because that path predates the remote work
  and is still implemented as the original BIO thread pipeline in src/backup/bio.rs,
  dispatched from src/backup.rs:446.

  3. Yes, that is the right direction. The current code is only partially there.

  You already have the beginning of that refactor:

  - shared control-file path mapping in src/backup/aio/entry.rs
  - shared local file helpers in src/backup/aio/local_fs.rs

  So architecturally, backup should become:

  - a SourceReader trait: read_file, maybe read_link, stat/open
  - a TargetWriter trait: mkdir, write_file, symlink, hardlink, delete, set_mtime
  - one generic copy executor over SourceReader + TargetWriter
  - target-specific post-copy phases either folded into TargetWriter or kept as target
    adapters

  Why it is not fully there yet:

  - local BIO and remote AIO are still separate execution models
  - post-copy phases are target-oriented, not source-oriented
  - local target phases currently reuse old control-file readers directly, while NFS/SMB
    target phases use transport-specific helpers
  - source/target path layout is still encoded in direction-level orchestration

  So the answer is: yes, we can and should reduce the combination explosion, but the clean
  abstraction is not “one file per direction”; it is “generic pipeline + transport adapters.”
  The current local_to_nfs, smb_to_local, etc. are transitional code, not the ideal final
  shape.
